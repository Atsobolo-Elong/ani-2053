Constat :
La compilation du programme est réussie avec Jenga en configuration Debug, avec la chaîne de compilation clang-mingw pour Windows x86_64. La première exécution, correspondant à la version corrigée, se termine normalement en environ 0,30 seconde. Les deux threads acquièrent successivement les mutex m1 puis m2, et le message « Programme termine sans interblocage. » est affiché.

Lors de la deuxième exécution, la version volontairement incorrecte reproduit l’interblocage. Le thread A acquiert m1, tandis que le thread B acquiert m2. Ensuite, le thread A attend m2 et le thread B attend m1. Le programme reste bloqué et ne termine pas normalement.

Pause :
Dans la version avec interblocage, le thread A est bloqué sur la ligne qui tente d’acquérir m2 avec NkScopedLock<NkMutex> verrou2(m2). Le thread B est bloqué sur la ligne qui tente d’acquérir m1 avec NkScopedLock<NkMutex> verrou1(m1). Les numéros exacts de ces lignes doivent être relevés dans le débogueur pendant la pause de l’exécution.

Correction :
La correction consiste à imposer le même ordre d’acquisition des mutex aux deux threads : m1 puis m2. Les deux mutex, les verrous de portée NkScopedLock et les pauses de 100 ms sont conservés. Ainsi, un thread ne détient plus m2 en attendant m1 pendant que l’autre détient m1 en attendant m2. La version corrigée compile et se termine normalement.

Règle :
Lorsqu’un programme utilise plusieurs mutex, tous les threads doivent les acquérir dans un ordre global cohérent. Si un thread acquiert m1 avant m2, les autres threads qui utilisent ces deux mutex doivent respecter le même ordre. Cette règle évite le cycle d’attente circulaire responsable de l’interblocage. Les verrous de portée permettent ensuite de libérer automatiquement les mutex à la sortie de leur portée.
